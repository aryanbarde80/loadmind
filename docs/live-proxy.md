# Live HTTP proxy mode

LoadMind's simulator remains the default browser-only experiment lab. Live Proxy is a separate, optional Node.js mode for routing real HTTP requests across HTTP(S) upstreams.

## Local development

```bash
npm ci
npm run dev
```

The one-command runner starts:

- Vite on `http://localhost:5173` (UI)
- the Node API/reverse proxy on `http://127.0.0.1:8787`
- three independent demo services on `127.0.0.1:9101`, `:9102`, and `:9103`

Vite proxies `/api/*` and `/proxy/*` to the API, so the browser uses same-origin relative URLs. No browser code calls localhost directly. Open **Live HTTP Proxy** from the welcome screen or the globe button in the app navigation.

## Demo upstream routes

Each demo service responds to:

| Route | Behavior |
|---|---|
| `GET /healthz` | Health-check response; excluded from request metrics |
| `GET /api/info` | Returns the selected service identity, region, and measured demo delay |
| `GET /api/slow?delayMs=260` | Artificially delays up to 1 second for latency experiments |
| `GET /api/fail` | Intentionally returns HTTP 503 so failure accounting can be exercised |
| `POST /api/echo` | Echoes method and body (up to 1 MiB) for request-forwarding tests |

These are real TCP/HTTP calls between separate Node servers. Their response times and routing are not generated by the browser simulation.

## Request and telemetry flow

```text
Browser ── /proxy/* ──> LoadMind HTTP server ── routing strategy ──> selected upstream
                              │                                      │
                              ├── /api/live-proxy/status             └── HTTP response
                              ├── /api/live-proxy/algorithm
                              └── /api/live-proxy/reset
```

The server strips the `/proxy` prefix, then preserves the incoming method, path, query, and body when forwarding. It creates a request ID and returns `X-LoadMind-Upstream`, `X-LoadMind-Request-Id`, and `X-LoadMind-Algorithm` response headers. Hop-by-hop headers are filtered. HTTP and HTTPS upstream URLs are supported; embedded URL credentials are rejected.

The proxy registry is independent of the simulator's TypeScript registry. It implements Round Robin, Weighted Round Robin, Least Connections, Weighted Least Connections, IP Hash, weighted Random, Least Response Time, Consistent Hashing, and Autopilot. Autopilot is deterministic and explains its current choice from observed latency spread, in-flight load, and node weights; it is not a remote AI call.

Health checks run every five seconds by default. A node is removed from routing after two consecutive failed checks and becomes eligible after a successful check. Operators can adjust each node's weight from 1–10 and drain or resume it without restarting the process; draining only stops new selections, so in-flight requests finish normally. The default upstream request timeout is five seconds. There are no automatic retries: a failed request is reported to the caller and the metrics.

## API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/health` | Process liveness |
| `GET` | `/api/live-proxy/status` | Strategy, actual request counters, latency percentiles, upstream health, and up to 40 recent events |
| `POST` | `/api/live-proxy/algorithm` | Set `{ "algorithm": "least-response-time" }` |
| `PATCH` | `/api/live-proxy/upstreams/{id}` | Change `{ "weight": 4 }` and/or `{ "draining": true }` for one configured node |
| `POST` | `/api/live-proxy/reset` | Reset proxy counters and recent events |
| `ANY` | `/proxy/*` | Forward a request through the selected strategy |

An OpenAPI 3.1 description is at [`openapi.yaml`](./openapi.yaml).

Metrics are in-memory and process-local. Latency percentiles use the most recent 500 completed requests; the event list is capped at 40. The event log omits request bodies and query strings. The status API does not disclose configured upstream URLs. A custom URL path can still contain sensitive identifiers, so avoid putting secrets in URL paths.

## Configure your own upstreams

Set `LOADMIND_UPSTREAMS` to a JSON array. Each item needs a unique, header-safe `id` and an HTTP(S) `url`; `name`, `weight` (1–10), and `healthPath` are optional. URLs with embedded credentials or query strings are rejected.

```dotenv
LOADMIND_DEMO_MODE=false
LOADMIND_UPSTREAMS='[{"id":"api-a","name":"API-A","url":"http://127.0.0.1:8080","weight":2,"healthPath":"/healthz"},{"id":"api-b","url":"http://127.0.0.1:8081","weight":1}]'
LOADMIND_ALGORITHM=weighted-round-robin
```

The Node entry points load a local `.env` file if present; begin with `.env.example`. Do not commit secrets. `LOADMIND_UPSTREAMS` replaces the demo pool. The configured services must be reachable from the LoadMind Node process or container.

For IP Hash or Consistent Hashing, the balancer uses `X-LoadMind-Key` if supplied; otherwise it uses the socket address visible to the Node process. Behind another proxy, that socket address may be the ingress/load-balancer address shared by many clients.

## Operator controls and deployment

In local development, operator controls are available to the local Vite-to-API connection. In production:

- Set a long random `LOADMIND_ADMIN_TOKEN` to enable remote strategy changes and metric resets using `Authorization: Bearer <token>`.
- If no token is set, operator changes are restricted to loopback connections. Remote status and proxy requests remain available.
- The UI keeps an entered bearer token only in component memory; it is not stored in localStorage.

Build and run without Docker:

```bash
npm run build
npm start                         # serves UI + API + demo upstreams on port 4173
```

Or build the included multi-stage image and run it with Compose:

```bash
cp .env.example .env              # set LOADMIND_ADMIN_TOKEN before public exposure
# optionally edit LOADMIND_UPSTREAMS and LOADMIND_DEMO_MODE
docker compose up --build
```

The container serves the built UI and API from one Node process; demo upstreams bind to loopback inside the container. Configure TLS at a trusted ingress/load balancer in front of it. Do not treat this learning-oriented proxy as a hardened internet edge: it has no TLS termination, retry budget, distributed state, rate limiting, circuit breaker, or per-tenant authorization. Protect the deployment at the network boundary and use an operator token whenever it is reachable beyond localhost.
